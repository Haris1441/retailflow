Chapter 2

Why batches were not dynamic

A new BigQuery batch (say BATCH_009) needed three manual steps before Phase 14:

  • The loader only accepted BATCH_001 to BATCH_008 (a fixed list of choices in the command).
  • It refused a batch whose row count was not in its CHANGE_COUNTS table.
  • Reconciliation failed until someone added the batch to the source_manifest seed.

Those guards were deliberate (an unexpected or half-written batch could not slip in), but they meant a human was the trigger and the source of truth for counts. Batch IDs like BATCH_009 also break at 1000, because text comparison puts BATCH_1000 before BATCH_999.

Everything after Bronze was already dynamic: Silver, history, Gold and reconciliation handle any batch in any order. Only the front door needed work.

Chapter 3

The file-driven flow

This is how most real platforms receive data. The client uploads files (usually over SFTP); the platform reacts to each file, checks it, loads it and records what happened.

  L --> T["dbt build
(manual, or dbt Cloud API)"]

Every path ends in a registry row and a folder, so nothing is ever silently dropped.

The important design choice: the Bronze load itself did not change. A file is turned into the same records the BigQuery loader produced, and goes through the same MERGE that skips records already present and writes its audit row in the same transaction. Phase 14 only added a new way of starting it.

Chapter 4

The file contract

A contract is the agreement between the client and the platform about how files look. Ours has three parts.

1. The file name

retailco_customers_20250301T090000_001.jsonl
│        │         │               │   └ format: one JSON record per line
│        │         │               └ sequence number within the delivery
│        │         └ delivery timestamp → batch ID BATCH_20250301T090000
│        └ entity (feed)
└ client prefix

Each feed has a regex in FILE_CONFIG, for example:

retailco_customers_(?P<batch_ts>[0-9]{8}T[0-9]{6})_(?P<seq>[0-9]{3})[.]jsonl

The pipeline tries every enabled pattern against the whole file name. Exactly one must match; none or two means REJECTED. The named group batch_ts becomes the batch ID, so batch IDs are timestamps that always sort correctly. Adding a new feed is adding one row to the table.

2. The control file

{"file_name": "retailco_customers_20250301T090000_001.jsonl", "row_count": 3, "sha256": "9f2c…"}

The client writes it after the data file. That solves two problems at once:

  • Half-uploaded files are never read. The pipeline waits until the control file exists.
  • Damaged or edited files are caught. The SHA-256 checksum and the row count must match what the client declared.

3. Each line (the record envelope)

{"entity": "customers", "source_record_id": "BATCH_20250301T090000:customers:1000:1",
 "business_key": "1000", "operation": "UPDATE",
 "effective_at": "2025-03-01T09:00:00Z", "source_available_at": "2025-03-01T09:00:00Z",
 "payload": {"customer_id": 1000, "loyalty_tier": "GOLD", …}}

This is the same shape as the BigQuery change tables, which is why Silver, history and Gold accept file records with no model change. One bad line rejects the whole file.

Chapter 7

What happens downstream

No staging, Silver or Gold model changed. File records carry SOURCE_SYSTEM = 'BIGQUERY' because they come from the retailer's core system; only the transport differs, and the registry records that. So a normal dbt build takes them in:

Silver versions

The file's version of customer 1000 arrived last, so it becomes ACCEPTED and the older one SUPERSEDED.

Incremental events

Events 14400 and 14401 happened on 8 Feb but arrived on 1 Mar. The incremental model uses arrival time, so it still picked them up.

History (SCD)

Customer 1000 went from SILVER to GOLD. Type 2 closed the old row at 2025-03-01 09:00 and opened a new one; Type 3 shows SILVER as the previous tier.

Gold

New sales would join to the GOLD tier, past sales keep SILVER. Product price changes affect future sales only.

Reproducing earlier resultsThe file batches are real new data, so Phase 11 and 12 expected values no longer match exactly. File batch IDs sort after BATCH_008, so building with --vars '{cdc_through_batch: BATCH_008}' (and a full refresh of the two incremental models) recreates the Phase 13 state.
Chapter 8

Failure and recovery

Recovery is simple because every step is safe to repeat: the Bronze MERGE skips records already present, a load is one transaction, and only a LOADED registry row counts as done.

SituationWhat you seeWhat to do
Wrong row count or checksumFAILED, file in error/, warning in dbtAsk the client to resend. A successful attempt with the same name closes the issue
Process stopped mid-fileRECEIVED, file in processing/Run scan again. It moves the file back and loads only what is missing
Client resends a loaded fileSKIPPEDNothing; that is the point
Unknown file nameREJECTED in the work listAgree the name with the client, or add a FILE_CONFIG row for a new feed
Same record ID, different contentFAILEDCorrections must arrive as a new batch, never as an edited old file
dbt build fails after a loadData safe in BronzeFix and rerun; every model rebuilds from Bronze

Reconciliation and monitoring

Reconciliation gained a step at the very start of the chain, and the expected counts for file batches now come from the client's own control files instead of a hand-edited seed.

flowchart LR
  F["Landed file

  B <-->|"2"| A["Load audit"]
  B -->|"3"| S["Silver"]
  S -->|"4 rows, 5 money"| G["Gold"]

Step 0 checks: control file count = rows read = rows its audited Bronze run extracted, and inserted and matched counts agree.

mon_file_feeds

One row per feed: files loaded, skipped, failed, open failures, rows inserted, last load, freshness (ON_TIME, LATE, NO_FILES_YET) and health.

mon_open_file_issues

The operator's work list. Empty means nothing to do.

assert_no_open_file_failures

A warning-level test. The build publishes what loaded but warns while a failed or stuck file is unresolved.

Chapter 11

The Azure Data Factory version

You asked where dbt fits if Azure Data Factory (ADF) runs the pipeline. The answer: ADF moves files and runs steps in order; dbt still only transforms data inside Snowflake. ADF's last step is to start the dbt job.

flowchart LR
  C["Client"] --> L["ADLS landing/inbox"]
  L -->|"Blob created event"| T["ADF trigger"]
  T --> P["Script: CALL PROCESS_LANDED_FILE"]
  P -->|"Snowflake reads the file
through a storage integration"| SF[("Snowflake Bronze")]
  P --> MV["Copy + Delete to archive/ or error/"]
  MV --> D["Web activity: dbt Cloud job"]
  D --> DB["dbt build in Snowflake"]

We wrote the full design as code, ready to deploy:

  • azure/deploy.ps1: resource group, ADLS storage, Key Vault, Data Factory and all access rights.
  • azure/adf/: linked services, dataset, pipeline and storage event trigger as JSON.
  • sql/snowflake/01_control/azure_landing.sql: the storage integration, the stage, a Python stored procedure with the same checks as the local pipeline, and a key-pair service user for ADF.
  • azure/client.ps1 and azure/trigger.ps1: the client uploads and the trigger switch.
Why it was not deployedWe installed Azure CLI and signed in, but the account had no Azure subscription. The free account had already been used and you chose not to switch to pay-as-you-go. SFTP on Azure Blob storage would also have cost about $0.30 per hour while switched on. The code stays in the repository as infrastructure as code, and the local pipeline proves the same design.
