How RetailFlow moves a fictional retailer's data from BigQuery to trusted reports in Snowflake

This guide explains the whole project as if you have never seen a data warehouse: what each piece is, why it exists, how a single order travels from the source to a revenue number, and which parts are dynamic versus written by hand.

Chapter 1

The basics: what problem are we solving?

Imagine an online and in-store retailer. It sells products in 4 countries (US, Pakistan, UK, UAE) through 12 stores, each a store, website or mobile app. Its data lives in two places: a BigQuery database (orders, customers, products and 12 more tables) and a small web API (a second sales channel). Managers want questions answered such as "what was net revenue in January?" or "which loyalty tier spends most?".

Raw source data cannot answer that safely. It has duplicates, late corrections, deleted records, broken references and amounts in four currencies. RetailFlow is a data platform that copies the data into Snowflake (a cloud data warehouse), cleans it in stages and proves the final numbers are correct. All data is synthetic, generated by us with deliberate defects so every problem can be demonstrated.

Words you will see everywhere

Data warehouse
A database built for analysis rather than for running the shop. Snowflake is ours: database RETAIL_DWH, compute warehouse RETAILFLOW_WH.
Schema
A folder of tables inside the database. We have BRONZE, STAGING, SILVER, DATA_QUALITY, GOLD, CONTROL and AUDIT.
Medallion layers
Bronze = raw copy, exactly as received. Silver = cleaned, one trusted row per real-world thing. Gold = report-ready tables and metrics.
ELT
Extract and Load first (Python copies raw data in), Transform later inside the warehouse (dbt). The opposite of transforming before loading.
dbt
A tool that runs SQL SELECT statements in a sensible order and saves each result as a table or view. Each SQL file is a model. We run it in dbt Cloud from the GitHub repo Haris1441/retailflow.
Batch
One delivery of source data. BATCH_001 is the starting snapshot; BATCH_002 to BATCH_008 are later changes.
Business key
The ID the business uses, such as order 10040. Many deliveries can share one business key (the order was created, then updated, then cancelled).
Idempotent
Running the same thing twice gives the same result as running it once. Essential for safe retries.

Chapter 4

Getting data into Snowflake (the Python loader)

This is the "Extract and Load" in ELT. dbt plays no part. The Python package ingestion reads from BigQuery (or the API) and writes into Snowflake. Every source record becomes one row in a single table, wrapped in a standard envelope:

Envelope columnMeaningExample
source_systemWhere it came fromBIGQUERY or MOCK_API
entityWhich source tableorders
source_record_idUnique ID of this physical deliveryBATCH_003:orders:40:1
business_keyThe business ID inside it40
batch_id, source_operationWhich delivery, and INSERT / UPDATE / DELETEBATCH_003, UPDATE
source_effective_atWhen the change happened in the business2025-02-17
source_available_atWhen the change arrived2025-02-18
run_id, ingested_atWhich load wrote it, and whena UUID
raw_payloadThe original record, untouched, as JSON{"order_id": 40, ...}

Why one table for everything? Loading never breaks when a source adds a column, because the payload is stored as JSON. Every row can be traced to its batch and load. Interpretation happens later in dbt, where it can be changed and re-run.

How one load works

  1. Extract the records for one source and batch, and stage them in a temporary Snowflake table.
  2. Check the stage: not empty, nothing lost, no record ID with two different contents.
  3. MERGE into Bronze on (source_system, entity, source_record_id): insert only records not already there. Re-running the same batch therefore inserts 0 rows. That is what makes retries safe (idempotent).
  4. Write one row to AUDIT.BRONZE_LOAD_RUNS (extracted, inserted, matched) in the same transaction, so the audit can never disagree with Bronze.

Watermarks: loading only what is new (Phase 6)

For the API, the pipeline CLI reads its settings from Snowflake tables instead of code. CONTROL.ENTITY_CONFIG says, per entity, which field marks change (updated_at), how much to overlap (60 minutes) and whether it is enabled. CONTROL.WATERMARKS remembers the last successful point. A run reads from watermark minus overlap, loads, and only then advances the watermark. If a run fails, the watermark stays put and the next run simply tries again. The overlap re-reads a little old data on purpose; the idempotent MERGE turns those into harmless matches.

Where Fivetran fitsFivetran is a paid tool that does this Extract-Load job for you. We set it up in Phase 7b as an independent comparison landing in its own schema, but BigQuery Sandbox blocks the change detection it needs without billing, so it is paused. It is not part of the main pipeline.
Chapter 5

How dbt works in this project

A dbt model is one .sql file containing a single SELECT. dbt wraps it in CREATE TABLE ... AS (or a view) and runs it in Snowflake. Models refer to each other with {{ ref('model_name') }} and to raw tables with {{ source('bronze', 'source_records') }}. From those references dbt builds a dependency graph and runs everything in the right order.

95 models

SQL files that create views or tables.

4 seeds

Small CSV files loaded as tables: the API crosswalk, the rule catalog, waivers, the source manifest.

170 tests

Queries that must return zero rows: unique keys, valid references, balances, reconciliation.

8 macros

Reusable SQL functions written in Jinja, so the same logic serves 20 entities.

Chapter 6

Staging: turning JSON into columns

There is one staging view per source entity: 15 for BigQuery (stg_bq_*) and 5 for the API (stg_api_*). Each does three things:

  1. Filters Bronze to its source and entity, through the bronze_source macro.
  2. Pulls fields out of the JSON and gives them proper types, safely. try_to_number(raw_payload:order_id::string) returns NULL instead of crashing on a bad value.
  3. Keeps the envelope columns, so every row still knows its batch and arrival time.
-- stg_bq_orders.sql (simplified)
with source_records as ( {{ bronze_source('BIGQUERY', 'orders') }} )
select
    source_record_id, business_key, batch_id, source_operation, source_available_at,
    try_to_number(raw_payload:order_id::string)              as order_id,
    try_to_number(raw_payload:customer_id::string)           as customer_id,
    upper(trim(raw_payload:order_status::string))            as order_status,
    try_to_decimal(raw_payload:order_total::string, 18, 4)   as order_total,
    try_to_timestamp_tz(raw_payload:fulfilled_at::string)    as fulfilled_at
from source_records

Staging still contains every delivery, including duplicates and bad ones. Deciding what is true happens in Silver.

Chapter 7

Silver: one trusted version of each thing

Order 40 arrives twice: as PENDING in BATCH_001 and as COMPLETED in BATCH_003. Event 17 arrives twice with identical content. Event 401 arrives, then a DELETE arrives for it. Silver has to decide what is currently true. The resolve_versions macro does this for every entity. It is called by the 20 int_*__versions models.

The rules, in order

  1. Order by business time. Use when the change happened (source_effective_at, else the record's own updated_at), not when it arrived. A correction dated January that arrives in March is still a January change.
  2. Spot duplicates. If a delivery's content matches the delivery just before it, it is a copy. Content is compared as a hash of the typed business columns.
  3. Push rejected changes to the back. A delivery that failed a quality rule can never be current (Chapter 8).
  4. The top-ranked delivery wins. If it is a DELETE, the key has no current row.

Every delivery gets exactly one disposition

DispositionMeaningExampleBigQuery count
ACCEPTEDThe current trusted versionOrder 40 as COMPLETED126,305
SUPERSEDEDAn older version replaced by a newer oneOrder 40 as PENDING1,048
DUPLICATEAn identical copy of the previous deliveryThe 240 re-sent events240
REJECTEDFailed a quality ruleProduct 31 with price −121
DELETEDThe latest version is a deleteEvent 4011

These dispositions are stored in silver_record_dispositions, one row per Bronze delivery. Their total must equal Bronze exactly, 127,655, and a test enforces it.

The 21 Silver tables then select the ACCEPTED rows and give them clean keys. A key such as BIGQUERY:40 carries its source, because the API and BigQuery are separate systems. Nested API arrays (order items, discounts, shipments) are flattened into their own child tables, one array per table so rows never multiply. The api_crosswalk seed maps API product and store IDs to BigQuery's.

Chapter 8

Data quality: reject, warn, quarantine, waive

18 rules live in the dq_rules seed. Their logic lives in 8 check models under models/data_quality/checks.

REJECT 13 rules

Run on every delivery, before the winner is chosen. A rejected change can never become current; the last trusted version stays. Negative price, missing category, category loop, negative stock, zero quantity, impossible return, missing customer, wrong order total.

WARN 5 rules

Run on current rows and only reported. Missing or malformed email, shared email, missing product description, missing supplier contact.

  • Quarantine (dq_quarantine): every rejected delivery with its raw JSON and the reason, for example returned=99, sold=2. 21 rows, all OPEN.
  • Waivers (dq_waivers seed): a person can approve an exception (rule, reason, approver, date). The failure stays on record; only its effect changes.
  • Publication status (silver_order_publication): PUBLISHABLE, HELD (trusted header but a rejected line, order 20) or QUARANTINED (no trusted header, orders 10 and 30). Gold publishes only PUBLISHABLE orders.
Why reject before choosing?If you take the latest version first and filter bad rows afterwards, the good older value is already gone. Ranking rejected deliveries last means products 31–45 automatically keep their January prices.
Chapter 9

Incremental processing and CDC

"Incremental" means processing only what changed instead of everything every time. It happens at two levels, which are easy to confuse:

LevelToolWhat decides "new"Safety net
Source → BronzePython pipelineCONTROL.WATERMARKS, the last loaded updated_at, minus a 60-minute overlapMERGE on record ID, so a re-read inserts nothing
Bronze → Silverdbt incremental modelsThe table's own highest last_delivery_available_atRebuild each affected key from all of its deliveries

How an incremental dbt run works

sequenceDiagram
  participant D as dbt run
  participant T as silver_payments (existing table)
  participant S as stg_bq_payments
  D->>T: watermark = highest last_delivery_available_at
  D->>S: which business keys have a delivery that arrived after the watermark?
  S-->>D: 100 keys (the late BATCH_006 payments)
  D->>D: re-rank ALL deliveries of those 100 keys
  D->>T: delete the old rows of those keys, insert the new rows
  D->>T: post-hook deletes keys whose winner is now DELETED or REJECTED
  • Arrival time, not business time. The late BATCH_006 payments happened on day 9 but arrived on day 54. A watermark on payment date would skip all 100. Arrival time only moves forward.
  • Rebuild the whole key. A late record still lands in the right place in its key's history.
  • Why only two tables are incremental. Payments and events depend only on their own deliveries. Products and orders do not: a category change can reject a product with no new product delivery, so "only new keys" would be wrong for them. They stay full rebuilds.

The CDC simulation

All batches are already in Bronze. The dbt variable cdc_through_batch hides later batches, so you can replay history as if each batch were arriving live:

dbt build --select tag:staging tag:silver --full-refresh --vars '{cdc_through_batch: BATCH_002}'
dbt build --select tag:staging tag:silver --vars '{cdc_through_batch: BATCH_004}'   -- rewrote 502 payments
dbt build --select tag:staging tag:silver --vars '{cdc_through_batch: BATCH_008}'   -- 100 payments, 250 events

Phase 10 proved, with content hashes, that the incremental result is identical to a full rebuild, and that replaying changes nothing.

Key business rules inside fct_sales

  • Booked merchandise = quantity × price − line discount − this line's share of the order discount. Tax and shipping are excluded.
  • Recognized when the order is fulfilled and not cancelled, pending or deleted, on the UTC fulfillment date.
  • USD conversion uses the exchange rate of the event date. Local amounts are only added within one currency.
  • Cost is the product cost at order time, from the product history.
  • Point-in-time keys customer_sk and product_sk point to the dimension version valid when the order was placed.

Chapter 14

What is dynamic and what is hard-coded

"Dynamic" means the value is worked out from data or settings at run time, so it adapts without a code change. "Hard-coded" means a person wrote it into a file, and changing it needs a commit.

Dynamic: works it out by itself

ThingDriven by
API loading windowCONTROL.ENTITY_CONFIG (watermark field, overlap, enabled) and CONTROL.WATERMARKS; change a row, not code
What gets inserted into BronzeThe MERGE compares record IDs, so re-runs need no special handling
