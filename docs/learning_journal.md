## Phase 0

BigQuery query jobs, Python transfer and Snowflake transformations have separate authentication and failure boundaries. Ingestion can succeed while transformation fails. A durable load checkpoint and a separate pipeline status let the operator recover from that distinction.

A duplicate delivery, a duplicate business key and a new version require different treatment. Preserve source evidence first and define the business grain before selecting the survivor. In an interview, trace an order with two lines and two payment attempts to explain why grain matters for revenue.

## Phase 7

dbt only transforms data that is already in the warehouse. A failed build after a successful load is a transformation failure, so Bronze and the CONTROL watermarks stay correct and you only rerun dbt.

Two failures came up while connecting dbt Cloud, and both are worth knowing for interviews. First, the role in the dbt Cloud credentials was `RETAIL_DBT_ROLE`, not the role the grant script prepared. When every model fails within seconds, check identity and grants before the SQL: `select current_role()` from inside the tool shows which role is really in use. Second, Snowflake `TRY_` conversion functions accept only string input. `try_to_number(raw_payload:customer_id)` passes a VARIANT and fails at compile time, while `try_to_number(raw_payload:customer_id::string)` keeps the intended behavior: malformed values become null instead of failing the run. `dbt parse` cannot catch either problem, because neither is visible until the SQL reaches Snowflake.

BigQuery needed four separate grants for Fivetran: Job User and Read Session User on the project, Data Viewer on the source dataset, and Data Editor on a separate working dataset for the helper tables Fivetran uses to detect changes. ## Phase 8

Silver separates three questions that staging leaves mixed together: which delivery is the current version, which deliveries are copies, and which keys were deleted. Order versions by business time, not arrival time. A backdated correction arrives late but belongs early in history. Baseline rows had no envelope effective time, so each entity falls back to its own payload time. Without that fallback, the corrected PKR rate would have lost to the original.

Detect duplicates on typed business columns, not raw JSON text. Two systems can serialize the same value differently. Give every physical delivery exactly one terminal disposition, then prove it with a count that must equal Bronze. That single reconciliation catches dropped rows, double counting and broken unions at once.

Flatten each nested array in its own model with its own key. Flattening two sibling arrays in one query multiplies their rows. The 16 API order lines and 8 shipments stayed exact because each was flattened separately.

Taking the latest version is not the same as taking the latest *trusted* version. Phase 8 deliberately let the BATCH_005 negative prices become current, which shows why Phase 9 needs rule results before choosing the survivor.

## Phase 9

Check rules before choosing the current version, not after. If a bad change is only flagged once it is current, the good value is already gone from Silver. Ranking rejected deliveries after every trusted one keeps the last good version current automatically: products 31–45 kept their BATCH_001 prices and category 1 kept no parent. A key is quarantined only when it has no trusted version at all.

Separate severity from effect. REJECT rules decide what may become current; WARN rules only report. A missing email is worth knowing about, but it should not remove a customer.

Reference rules must check against trusted data, in a fixed order: categories, then products, then order lines, then orders and returns. A product pointing at a rejected category is as broken as one pointing at a missing category.

Cycle detection has to respect time. Checking the category tree as it stood when each change arrived blames only the change that closed the loop, not the older categories inside it.

Publication status is a separate decision from row validity. Order 20's other lines are valid records, but one rejected line means the order must not reach Gold yet. Holding it is more honest than silently dropping a line.

Waivers belong in Git with a reason, an approver and a date. The failure is still recorded and only its effect changes, so the audit trail survives.

## Phase 10

An incremental model has two separate jobs: finding what changed and recomputing it correctly. Find changes by arrival time, which only moves forward, never by business time. The 100 backdated BATCH_006 payments arrived on day 54 with a business date of day 9, so a business-time watermark would have skipped all of them. Then rebuild each affected key from its full history, not just the new row, so a late record still lands in the right place in the key's history.

`delete+insert` can only replace keys that appear in the new data. A hard delete leaves no new row, so the old row survives unless you write the key anyway and remove it afterwards. Here a post-hook deletes rows whose top version is not ACCEPTED.

Incremental is only safe when a key's result depends on that key's own deliveries. Payments and events qualify. Products and orders do not: a category change can reject a product with no new product delivery. Those need dependency expansion or stay full rebuilds.

Prove it rather than assume it: compare content hashes of the incremental result, a replay and a full rebuild, and check the work done in query history. The first validation attempt reused `--full-refresh` on every step and produced a meaningless "pass". A proof is only as good as the conditions it ran under.

Duplicates must be judged against the previous delivery, not any earlier one, or a value that changes back (A → B → A) gets lost.

## Phase 11

A Type 2 dimension is only as good as the time it uses. dbt snapshots stamp changes with the run time, so a late change lands on the wrong date and history before the first snapshot is gone. When every delivery is kept with its business time, history can be derived instead: a pure, rebuildable function of Bronze. Customer 12's backdated tier change sits on 2025-01-13, not on the day it arrived.

Choosing Type 1 or Type 2 per column is a business decision. Track an attribute when reports must group facts by its value at the time. Restate corrections such as names on every row. Leave noisy fields untracked: the addresses-only change for customers 101–109 created no history rows.

History must use trusted data only. A rejected price must not appear even as a closed period, or a point-in-time join could value a past sale at a price that was never valid.

Make validity intervals half-open (`valid_from` inclusive, `valid_to` exclusive), contiguous and with exactly one open row. Then a fact at any instant matches exactly one row, and a test can prove it.

Type 3 is cheap and answers "changed from what?" but keeps only one previous value. Derive it from Type 2 so the two can never disagree.

## Phase 12

A metric definition is a set of decisions, and each one has to be written down: which amount (merchandise excluding tax and shipping), which event date (fulfillment for sales, completion for credits, payment date for cash), which exchange rate (the rate on that date), and which population (publishable orders only). Two reasonable analysts make different choices here, which is why the glossary in business_rules.md comes before the SQL.

Allocate header amounts with an explicit rounding rule. Rounding each line share to cents and giving the remainder to one stable line keeps line totals equal to the header exactly, and a test can enforce it.

Store point-in-time surrogate keys on the fact at load. Then every report gets the historical tier and category for free and cannot accidentally join to the current values.

Validate against an independent implementation, not against Gold itself. A Python simulation built from the fixture rules agreed with Snowflake to the cent on every measure. Agreement between two separately written implementations is strong evidence. A query that re-derives a number from the same table is not.

Read a surprising KPI before calling it a defect. February's −95 % MoM is real for this data: the baseline orders fall in January.

## Phase 13

Reconciliation needs an independent expected value at the start of the chain. Comparing the warehouse with itself proves consistency, not completeness. The `source_manifest` seed is the outside reference. In production it would be a source-side control total, a file trailer or an API count.

Reconcile both counts and money. Counts catch lost or doubled records. Money catches a wrong join, a sign error or a currency mix-up that leaves counts intact. Reconcile money per currency, and never add AED to PKR. When a currency is not trusted (a quarantined header), give it its own bucket instead of guessing.

"Silver = Gold + exclusions" is only meaningful if exclusions are records with reasons. A single "excluded: 9" number can hide anything. A register lets an auditor trace each one back to its quarantine evidence.

An audit log written in the same transaction as the load can be reconciled exactly. It also documents history for free: the BATCH_001 partial re-run and the API replays show up as runs that matched rows and inserted nothing.

Put the check in the build, not in a document. `assert_reconciliation_passes` turns six layers of evidence into one pass/fail gate that runs every time.

## Phase 14

Real platforms rarely pull from a source on a timer. Clients push files, and the pipeline reacts. The parts that make that safe are boring and essential:
- a naming contract (a regex per feed, kept in a config table);
- a control file written last, so a half-uploaded file is never read;
- a checksum and row count, so a truncated or edited file is caught;
- a registry row for every attempt.

The file name is metadata. Feed, entity and batch come from it, so nothing is typed by hand and a new feed is a config row. Timestamp batch IDs sort correctly forever. `BATCH_009` style IDs break at 1000.

Idempotency makes recovery dull, and dull is good. The same content is skipped by checksum before loading. A file interrupted mid-run is simply processed again, and the Bronze MERGE inserts only what is missing. Each load is one transaction, so a failure leaves nothing half-done.

The expected count now comes from the file's own control file. It replaces the hand-maintained manifest, which is what a production reconciliation would use.

Orchestration tools (ADF, Airflow, Dagster) replace the trigger and the moves, not the design. The registry, the regex config, the MERGE and dbt stay the same. A local polling sensor and a storage event trigger are the same idea at different costs.

Monitoring is a table someone reads, plus an alert. `mon_open_file_issues` should be empty, and a warn-level test makes an unresolved failure visible in every build without blocking the data that did load.
